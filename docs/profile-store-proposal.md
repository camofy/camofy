# Profile 商店：社区资源调研与设计提案

状态：历史调研与设计提案，记录初始候选及分期建议，并非当前功能清单。首版精选商店已实施；当前行为以代码、迁移和 README 为准。调研日期：2026-09-16。

## 结论

把商店做成“经过适配、可组合、有版本的网络配置组件目录”，而不是任意 YAML / 脚本下载站。

社区通常提供规则数据和针对特定工具的模板，并非 Camofy Profile。Camofy 的价值是把来源、匹配条件、路由策略、依赖、客户端兼容性和更新风险整理好，使用户无需阅读 YAML 就能安全组合。

已有的“抖音与商城 DIRECT”是首个组件原型：社区域名数据 + Camofy 精选范围 + DIRECT 策略 + prepend-rules 插入语义。它不是对某个完整社区项目的原样转载，也不意味着社区有一个恰好相同的现成 Profile。

首版定位：官方精选的声明式规则包，支持安装、身份关联、预览、手动升级、锁定和回滚；不开放任意脚本执行、不收录免费代理节点、不处理 MITM 证书或响应重写。

### 许可是上架门槛

仓库页面分别声明了不同协议：例如 ACL4SSR 为 CC-BY-SA-4.0、AWAvenue 为 GPL-3.0；Sukka 文档声明主体为 AGPL-3.0，同时存在单文件许可例外。blackmatrix7 除 LICENSE 外还有额外使用声明。聚合仓库也不能替代其上游数据的许可来源说明。

以上仅为调查到的声明，不是再分发合规结论。每个候选版本必须记录：文件级许可、上游来源链、原作者、版权声明、修改说明、是否允许当前分发方式。声明不一致或授权不清晰的资源，先只保留候选索引，不下载后上架，更不能通过换一个镜像来源来回避审核。

## 2. 建议第一批商品

先精选 8～12 个组件，而不是把整个 GitHub 目录灌进商店。下列名称是 Camofy 拟提供的产品名称，不声称上游有同名成品。

| 组件 | 默认行为 | 首期范围/提醒 |
| --- | --- | --- |
| 抖音与商城直连 | DIRECT | 视频、图片、商城、支付；不自动扩大为整个字节生态 |
| 哔哩哔哩直连 | DIRECT | 国内版和国际版区分 |
| Steam 国内下载 | DIRECT | 下载 CDN 与商店/社区/登录分开，不能全部直连 |
| Apple 国内服务 | DIRECT | 采用国内分类，不把全部 Apple 服务认定为直连 |
| Microsoft 国内服务 | DIRECT | 国内分类，与海外服务分开 |
| 局域网访问 | DIRECT | 精选域名和私网 IP；提示其适用网络 |
| 纯广告拦截 | REJECT | 与隐私/推送/更新拦截分开；允许用户自建例外 Profile |
| Telegram 分流 | 选择策略组 | 包括所选来源支持的域名/IP，不承诺节点可用性 |
| AI 服务分流 | 选择策略组 | 首选单服务可勾选，不保证地区限制或账号风控可绕过 |
| Netflix / YouTube 分流 | 选择策略组 | 可以分别安装；不承诺选定节点具备解锁能力 |

重复来源是备选，不是默认叠加：一个商品默认选一套经过审核的来源策略，必要的补充数据须记录来源和目的。广告包、地区全集尤其不应同时装多套“大全”。

## 3. 不改变已有核心模型

继续维持“Profile 本身没有启用状态，启用/禁用属于身份关联”。新增三个概念：

1. **商店包 Package**：公共目录条目，如 douyin-direct，包含说明、来源、适配器、参数和权限声明。
2. **包版本 PackageVersion**：审核后不可变的内容与依赖快照，固定 commit/blob hash、编译器版本、许可记录和兼容结果。
3. **已安装 Profile**：租户持有的包实例，记录版本和更新偏好；仍能被多个身份引用。

身份关联仍保存 `profile_id`、`enabled` 和排序。可增加受限的 `parameters`，用于同一规则包在不同身份映射不同策略组。例如同一个 Telegram Profile 在手机身份选择“自动选择”，在工作身份选择“工作节点”。目标策略属于身份绑定，而非商店作者硬编码。

DIRECT / REJECT 类可使用包声明的默认值；需要代理组的包，在关联身份时必须选择真实存在的目标，禁止找不到时悄悄退回 DIRECT。

### 一个可评审的商品声明示例

以下只是新 schema 的示意，不是已发布接口，也不是可直接导入的 Clash 配置。真实版本必须附上已核验的提交、文件清单、内容哈希和文件级许可，不能保留浮动来源。

```yaml
id: camofy/douyin-direct
kind: rules
name: 抖音与商城直连
parameter-schema:
  policy:
    type: policy-reference
    default: DIRECT
    scope: identity-binding
capabilities:
  writes: [rules]
  network: false
placement: prepend
compatibility:
  mihomo: supported
  shadowrocket-full: requires-inline-validation
  shadowrocket-nodes: no-routing-effect
```

这里 `network: false` 约束的是组件实例化期间不执行外部请求；上游公共数据抓取属于独立的受控目录流程。下载、编译、客户端行为权限不能混为一谈。兼容标记也必须由测试更新，而不是只相信作者声明。

安装和启用分开：点击“添加到我的 Profiles”只生成实例，不改变任何身份；完成“关联身份→参数→合并预览→确认发布”才生效。私有 Profile 不会因为来自商店就变成公开资源。

## 4. 版本化编译链路

公共资源流程：登记来源 → 固定上游快照 → 解析/适配 → 依赖及许可检查 → 沙箱内静态测试 → 人工审核 → 发布不可变版本。

租户流程：安装已发布版本 → 绑定身份参数 → 生成受限配置片段 → 复用身份合并引擎 → 校验全部依赖/输出 → 原子发布 → 沿现有订阅和设备同步链路下发。

云端 API 不运行常驻 Mihomo。公共包的核心兼容测试可在 CI 的隔离环境运行，不上传用户订阅、节点密码或私人配置到公共 CI；用户组合做服务器静态验证，Agent 继续在本地使用 `mihomo -t`。第三方客户端的语义验证仍需真实导入测试。

### 统一中间表示，不直接执行上游文件

最小规则模型是结构化的 `匹配类型 + 匹配值 + 选项`，策略在身份关联时注入。例如域名集合不带 PROXY/DIRECT；Camofy 的组件定义决定默认行为与是否允许覆盖。

- 支持已知格式适配器：Clash classical list / YAML payload、domain/ipcidr provider、明确子集的 v2fly 文本。
- 同一资源树内的 include 固定到同一个上游提交，限制深度、数量并检测循环。
- 不把 Adblock 过滤表达式、Surge 重写、Quantumult X 脚本或 subconverter .ini 当作 YAML；无法完整转换则拒绝或明确标为不支持。
- MRS / Geo 二进制不是任意透明输入；优先以文本构建可审阅内容，二进制仅作为已知编译器产生的目标制品。
- 参数使用类型化 schema 和 AST 替换，不用字符串拼接注入 YAML、路径或 URL。

## 5. 与当前项目的具体差距

| 当前行为 | 商店带来的问题 | 设计要求 |
| --- | --- | --- |
| 只有 source / overlay 两类 Profile | .list、payload、远程依赖不能被普通 YAML 根节点校验正确理解 | 增加包解析/适配层，不放宽 source 订阅解析成任意格式 |
| rules 拼接；支持 prepend/append | 上游 MATCH 会遮住后续规则，多个 prepend 的先后容易误解 | MVP 规则包统一生成 prepend-rules；预览展示最终顺序，不静默重排既有 Profile |
| 普通字段后覆盖前；节点/组按名合并 | 公共包同名字段可能覆盖私人配置 | 公共包默认不写节点/代理组/DNS；未来新增组、provider 用实例命名空间，并同步改写引用 |
| validate 检查策略和部分引用，但未验证 RULE-SET 对应 provider 存在 | 会重现“规则集不存在，客户端不能启用” | 检查所有 provider/sub-rule 引用、类型、路径和依赖完整性 |
| Shadowrocket 完整导出只支持部分规则且要求内联 | 插入远程 RULE-SET 后 Clash 可用、Shadowrocket 报错 | 按输出格式编译，不能假装跨端通用；节点订阅不会携带规则 |
| 单份 YAML 上限 4 MiB | 大型广告/地区全集展开后超限，低配设备有内存压力 | 首期只收体积合适的规则包；明确字节/规则数预算，实测低配设备；大型制品走后续方案 |
| 每次资源修改重建租户全部身份 | 10 万用户关注同一包，更新会形成放大效应 | 建立反向依赖，异步分片仅重建受影响身份，去重任务并限速 |
| 历史配置仅有限数量，回滚后后续更新又能发布 | 包回滚后会被自动升级再次覆盖；旧依赖可能丢失 | 安装实例锁定版本，revision 保存包依赖清单；保留所有仍被引用的包和资源 |

注意：当前“系统 Profile 最后合并”与“系统保护规则最先匹配”同时成立，因为它使用 prepend-rules。商店不能引入一套不一致的全局优先级来改变这个合同。

### 规则优先级与冲突

保留现有身份顺序语义。规则组件推荐放在普通订阅之后，系统保护仍最后合并。由于 prepend 后应用的块会排前面，界面必须显示“最终优先级”，不能仅让用户猜列表排序。

MVP 禁止规则包携带 MATCH/FINAL、全局 mode、TUN、端口、网卡、路由标记、控制 API、secret 和上游代理节点。DNS 模块及完整模板属于第二期独立能力，需显式确认写入字段。

该限制只针对商店首批“规则包”的权限，不删减用户已有独立 Profile 的能力。“关闭 TUN”等运行参数组件可以继续通过个人 Profile 配置；要上架为系统调优商品时，应走单独的高级能力审核和客户端适用性说明。

对相同域名不同策略、明显的后缀覆盖、被 MATCH 遮挡、同名资源和不兼容字段提供冲突诊断。不要对规则全局排序、把“较具体规则优先”作为隐式改写，或跨策略去重。复杂逻辑、DNS/IP 动态匹配无法完全静态证明，必须说明诊断覆盖范围。

“抖音直连”与“广告 REJECT”可能有真实重叠：安装预览应显示具体冲突域名及谁优先。不得自动为了流畅而放开全部广告，也不得为了广告拦截覆盖系统云端保护。保留用户明确设置的身份顺序，并提供个人例外 Profile 的入口。

## 6. 配置和外部资源怎么下发

### MVP：内联、自包含

把审核通过的规则编译进最终 YAML，不让路由器再请求 GitHub，不新增端侧解析器或后台服务。小型应用包很适合这种方式，Shadowrocket 支持子集也更容易控制。超出大小或能力预算的商品先标记不可安装，不截断规则。

### 第二期：大型不可变资源

大包可生成 `https://<当前云端域名>/rules/<content-hash>/<format>`，对公共不可变文件使用 CDN 缓存。按客户端能力输出 Mihomo provider，或支持范围内的 Shadowrocket 内联结果；不支持时明确阻止对应格式发布，不静默丢规则。

这时“只下发一个 YAML、没有额外文件请求”的约束需要明确放宽；对配置来说仍由云端编译，但运行时会多一次规则文件获取。首期不依赖该变更。

版本锁定必须覆盖嵌套依赖。不能 YAML 固定 v1，里面却引用上游 mutable/latest 的规则 URL，否则回滚和跨设备一致性都是假的。资源 URL 使用配置的云端 origin，同域的系统 DIRECT 保护可沿用。

公共资源端点只提供已审核产物，不把现有 GitHub 下载转发扩展成任意 URL 开放代理。租户 YAML、机场 URL 和节点凭据绝不能进入公共 CDN 缓存。

## 7. 更新、撤回和回滚

- 上游更新只创建待审核候选版本，不修改现有已发布版本。
- 首版默认手动升级；后续可选择“自动跟随审核版”，也不直接跟随 GitHub HEAD。
- “配置语义新增、策略扩大、DNS/能力改变”与普通规则数据变化分开标识；即便只是域名更新也可能改变网络行为，不能简单保证补丁版本绝对安全。
- 展示新增/删除规则数、范围扩大、权限变化、兼容变化、影响的身份列表。
- 对一个安装实例升级，先基于版本检查编译它所关联的全部身份；有失败则本次升级不提交，实例和所有身份继续用旧版本。大规模更新按租户/安装实例小批次执行，不开全平台长事务。
- 开始发布前可对低风险测试身份灰度；使用已有应用失败报告判断配置应用质量，不收集用户域名访问日志。
- 回滚同时恢复包版本、参数及依赖快照，并默认锁定，防止下一次自动更新复发。
- 下架不等于立即删除：普通弃用只停止新安装；安全撤回应通知和阻止后续升级，不能未经明确策略把现有身份中的内容自动移除而导致断网。

## 8. 数据与接口建议

新增公共目录表与用户资源分离，不能把现有加密 resources 的 `user_id=NULL` 当作公共共享方案。

- `catalog_packages`：slug、作者/维护者、用途、类别、支持的客户端、风险、状态。
- `catalog_versions`：不可变版本、内容哈希、schema/编译器版本、来源/许可快照、参数 schema、能力声明、测试结果。
- `catalog_artifacts`：已批准原始快照和各格式产物的哈希、大小、存储位置、依赖清单。
- 用户现有 Profile 增加 `origin=store`、`package_id`、`installed_version`、`update_policy` 等服务端受控元数据；仍是租户资源。
- 身份 binding 增加类型化策略参数；发布 revision 保存完整 lock manifest。
- 依赖索引和任务 outbox：包版本→安装实例→身份，事务内安排任务、事务外限流重建。

候选接口：`GET /api/store/packages`、`GET /api/store/packages/:slug`、`POST /api/store/install`、`POST /api/profiles/:id/upgrade-preview`、`POST /api/profiles/:id/upgrade`、`POST /api/profiles/:id/fork`。安装和升级幂等、带乐观版本校验，所有写操作沿用租户鉴权和 CSRF 防护。

用户不能原地修改一个跟随商店的托管模板：可以改允许的参数、叠加个人 Profile，或“复制为独立 Profile”。复制后不再自动更新，保留来源说明；不做难以解释的任意 YAML 三方合并。

## 9. 前端体验

- `/store`：按用途、客户端、风险、已安装状态过滤。卡片显示“作用、默认策略、来源、更新日期、安装后影响”，不只显示仓库名。
- `/store/:slug`：说明、兼容矩阵、规则摘要、来源与许可、版本历史、权限、已知冲突；展示商品维护者和原规则作者，两者不能混淆。
- 安装向导：选版本→添加到我的 Profiles→可选关联身份→选择策略→查看变更→确认发布。选择目标身份后才有意义的策略组选项不能提前硬编码。
- `/profiles/:id`：托管来源、当前/可用版本、跟随策略、所关联身份、升级/锁定/回滚/复制独立入口。
- `/identities/:id`：继续管理启用、排序及参数；增加来源标记、冲突提示、最终规则顺序和版本变化说明。
- 所有页面使用现有真实路由，支持深链、刷新恢复、返回列表状态。删除已安装 Profile 前继续要求解除身份关联。

## 10. 多租户、规模与开源自托管

公共数据只拉取和编译一次，不能每位用户各自请求 GitHub；尤其不能为公共规则消耗用户的短效订阅代理。目录抓取使用运营方独立、受限的网络配置，不能读取租户代理凭据。

公共包转换缓存按源快照、编译器版本和格式共享；身份产物因节点凭据、参数、排序不同保留租户隔离。升级波次要有限流、退避、幂等和可恢复 checkpoint，下载制品先写成功再发布元数据，避免“有版本无文件”。

安全边界包括：来源 allowlist、SSRF/DNS 防护、受控重定向、不转发私有凭据；体积、规则数、解压比、include 深度、执行时间上限；目录文案转义、不注入 HTML；规则条目禁止未申报的网络目的地和配置字段。未知 Git 仓库的构建脚本不在云端执行。

开源部署可使用随版本附带的审核目录，离线继续使用已安装快照。官方更新目录可选启用，用签名 manifest 和配置的可信公钥验证来源，哈希验证内容；允许自托管管理员登记私有目录。验证密钥轮换需旧钥授权或管理员确认。安装时不要求注册官方云、不上传本地用户订阅。

## 11. 分期与验收

### 第一阶段：可用且可控

精选 8～12 个声明式规则商品；来源/许可审核；版本快照；规则解析；安装实例与身份策略映射；依赖校验；合并预览；手动升级与锁定回滚；完整路由页面。全部内联，不新增端侧功能。

### 第二阶段：扩展体积与模板

大型规则缓存和按能力输出 provider；经审核的自动升级；高级 DNS/fake-ip 模块；完整配置模板作为新身份创建向导，而不是能任意叠加的普通规则包。

### 第三阶段：社区提交

作者提交 manifest 和固定来源，由平台审核后上架；提供举报/弃用/撤回及维护者权限。任意脚本运行不在本方案的默认演进路线中，确有需求再单独设计隔离与权限。

验收至少覆盖：缺 provider、引用循环、策略组不存在、早期 MATCH 遮挡、同名资源、共享 CDN 域名冲突、超大包、include 环、恶意 URL、失败更新不覆盖旧版本、锁定后不自动升级、相同 Profile 多身份参数不同、目标格式不支持时明确失败、低配设备配置加载、租户/缓存隔离、自托管无官方账号、刷新不丢页面。

首版建议确认的决策：精选目录而非开放上传；规则包而非脚本平台；手动升级为默认；策略参数在身份关联上；有限体积内联保证端侧轻量化；上架前完成文件级许可审核。
